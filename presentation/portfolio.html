01

実現したかったこと（要件定義 / Objective）

🎯 開発背景と全体コンセプト

ハイスピードで進行する3Dレールシューティングにおいて、ゲームプレイの「戦略性」「快適な操作感」「ゲーム開発効率（データ駆動設計）」を確立することを目的とした。

  • 4種類の編隊（V字、円形、横一列、斜め一列）を組んだ組織的な敵飛行と自律ステートマシン
  • メモリリークやアロケーションオーバーヘッドを排した無限スクロール背景システム
  • ハイスピード下でもストレスを感じさせないエイムアシストと無敵回避アクション
⚠️ 直面した技術的課題（要件）

本開発において解決すべき4つのシステム・AI課題：

  • 【課題1】敵AIの組織感と計算効率: 単体敵AIによる交差や交戦のバラバラ感を防ぎ、1グループ最小更新コストで隊列を維持
  • 【課題2】無制限前進のメモリ管理: 毎フレームの動的生成・破棄（Instantiate/Destroy）によるメモリ断片化とコマ落ちの撲滅
  • 【課題3】ハイスピード下の命中率: 高速移動中（480m/s）の照準難易度を緩和する動的ターゲット吸着（エイム補正）の実装
  • 【課題4】レベルデザインの非コード化: プランナーがC++コードをビルドせずBlender上で難易度調整できるデータ同期構築

比較検討した技術・手法（Alternatives / 先行研究の到達点）

従来の手法における技術的限界（Gap）を指摘し、比較検討を行った。

① 敵AIの飛行制御手法比較

アプローチ案 メリット デメリット / 技術的限界 (Gap) 判定結果
A案: 敵単体ごとの完全独立自律AI 各敵が自由に行動可能 敵同士が交差し隊列が崩れ、個別のAI更新コストによりCPU負荷が増加（100体で > 2.1ms） 不採用
B案: 固定スプライン曲線アニメーション 綺麗な隊列を描ける 自機の移動や攻撃に動的反応できず、単調な「覚えゲー」になりアクション性が低下 不採用
C案: 相対座標オフセット行列 + 4状態AI 親行列1回の更新で編隊全体を計算量 $\mathcal{O}(1)$ 制御。特攻時は自律ダイブ 隊列離脱時・特攻時の座標補間処理が必要（※12フレームSlerpで解決） 採用 (本方式)

② ステージ背景描画・メモリ管理手法比較

アプローチ案 メリット デメリット / 技術的限界 (Gap) 判定結果
A案: 毎フレームの動的生成・破棄 自由なコース配置が可能 C++メモリ割り当ての断片化およびヒープ確保オーバーヘッドによるコマ落ちが発生 不採用
B案: 巨大固定ステージメッシュの一括読み込み 描画ロジックがシンプル 巨大なVRAMを消費し、無限前進コースに対応できない 不採用
C案: 48タイル・リングバッファプール + ビル積層 メモリ割り当てゼロ（完全アロケーションフリー）で無限ループ連続描画 Z軸再配置のワープ判定ロジックの実装が必要 採用 (本方式)
03

技術選定の理由と実装詳細（Motivation & Selection）

🛸 3.1 敵AIの「4種フォーメーション飛行」と「4状態ステートマシン」

【選定理由】 敵の隊列飛行（V字、円形、横一列、斜め一列）を低CPU負荷で制御するため、階層トランスフォーム（グループ中心座標からの相対オフセット行列）を採用。敵個体には 待機 (`kIdle`) ➔ 合流 (`kMerge`) ➔ 浮遊 (`kFloat`) ➔ 特攻 (`kDive`) の4状態ステートマシンを実装した。

C++ Implementation: GamePlayScene.cpp (抜粋) C++20 / DirectXMath 
// 敵フォーメーション相対座標の動的計算ロジック
void GamePlayScene::ApplyGroupFormation(size_t groupIndex) {
    auto& group = enemyGroups_[groupIndex];
    Vector3 center = group.centerPosition;
    
    for (size_t i = 0; i < group.enemyIndices.size(); ++i) {
        uint32_t enemyIdx = group.enemyIndices[i];
        Vector3 offset = Vector3(0, 0, 0);

        switch (group.formation) {
        case FormationType::kVShape: // V字隊列
            offset = Vector3((i % 2 == 0 ? 1.0f : -1.0f) * ((i + 1) / 2) * 3.0f, 0.0f, -((i + 1) / 2) * 4.0f);
            break;
        case FormationType::kCircle: // 円形隊列
            float angle = (DirectX::XM_2PI / group.enemyIndices.size()) * i;
            offset = Vector3(cosf(angle) * 8.0f, sinf(angle) * 8.0f, 0.0f);
            break;
        // 横一列・斜め一列の動的切り替え
        }
        
        // 親座標 + 相対オフセットによる一括行列変換
        enemyTransforms_[enemyIdx].position = center + offset;
    }
}
🧱 3.2 床48タイル・リングバッファプール ＆ ビル積層描画

【選定理由】 48枚の床オブジェクトを円環バッファ（Ring Buffer）構造で常駐させ、自機のZ移動に応じてカメラ後方に去ったタイルを前方へ `Z + TileSize * 48` だけループ移動させる設計を採用。1階〜5階までの構造パーツを個別に持つプロシージャルビル積層（Cascade Rendering）によりメモリを大幅節約した。

C++ Implementation: GamePlayScene.cpp (抜粋) C++20 / Object Pooling 
// 床タイルの無限ループ再配置ロジック
void GamePlayScene::UpdateInfiniteFloor(float cameraZ) {
    const float kTileSize = 40.0f;
    const int kTotalTiles = 48;
    const float kLoopLength = kTileSize * kTotalTiles;

    for (int i = 0; i < kTotalTiles; ++i) {
        float tileZ = floorPositions_[i].z;
        // カメラより一定距離後方に去ったタイルを前方にワープ再配置
        if (cameraZ - tileZ > kTileSize * 4.0f) {
            floorPositions_[i].z += kLoopLength;
        }
        // 定数バッファの変換行列を更新 (メモリ割り当て数 0 回)
        floorTransformData_[i]->WVP = MakeIdentity4x4() * MakeTranslate(floorPositions_[i]) * viewProjectionMatrix_;
    }
}
🎯 3.3 ターゲット吸着エイムアシスト ＆ ディゾルブ・アウトラインHLSL

ハイスピード下での命中感を高めるエイムアシスト（レティクル周囲のターゲット検索と球状弾道補正）と、D3D12レンダーターゲット分離によるピクセルシェーダーポストプロセスを組み込んだ。

HLSL Pixel Shader: Dissolve.PS.hlsl (抜粋) DirectX 12 HLSL 
float4 main(VSOutput input) : SV_TARGET {
    float4 mainColor = gTexture.Sample(gSampler, input.uv);
    float mask = gMaskTexture.Sample(gSampler, input.uv).r;

    // 閾値以下のピクセルをアルファテスト破棄 (Discard)
    if (mask < gDissolveParam.threshold) {
        discard;
    }

    // 消失エッジ部分の発光合成 (オレンジ・ネオン発光)
    if (mask < gDissolveParam.threshold + gDissolveParam.edgeRange) {
        mainColor.rgb += gDissolveParam.edgeColor * 2.0f;
    }

    return mainColor;
}
04

結果とトラブルシューティング（Result & Reflection）

🛠️ トラブルケース: 高速特攻敵 (kDive) におけるすり抜け衝突判定の解消

敵が特攻ダイブ（180m/s以上）に移行した際、1/60秒のフレーム間で自機を飛び越えてすり抜けるバグを解決したプロセス。

STEP 01: 失敗 (Problem)

判定すり抜けバグ

高速特攻敵が自機のAABB衝突判定をすり抜け、ダメージが正しく適用されない現象が発生。

STEP 02: 特定 (Diagnosis)

フレーム離散解析

1フレームの移動量 ($\Delta s = v \cdot \Delta t$) が判定球の半径を超過していることを特定。

STEP 03: 改善 (Fix)

スイープ球判定導入

前フレームから現在位置までの軸を「Capsule/Swept Sphere」としてレイキャスト幾何判定。

STEP 04: 知見 (Reflection)

連続衝突判定 (CCD)

ハイスピードゲームにおける幾何衝突判定の連続性と計算軽量化手法を獲得。
